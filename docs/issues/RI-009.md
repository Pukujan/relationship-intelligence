### Summary
The product now has a defined command surface: a console where one person directs a team of AI agents (sales, marketing, research, and more) that work the relationship graph. This records the accepted goal, operating model, and UX map so the UI and intelligence work have one canonical target instead of drifting. It captures the owner's direction that agents help figure out the work (naming, objectives, research), the human always decides, deadlines and iteration prevent silent stalls, and state is represented as legible signals.

## PDD
A person signs in (Google via Octo, or as a guest into a demo), lands on a personal Today view, and directs agents through one copilot reachable by typing, voice, or a phone call. Work is organized as Project → Objective → Mission → Plan; people/companies/events stay a single evidence-backed graph that work references. Agents research and propose mission names, measurable objectives, and plans; the human edits and approves before anything becomes work or sends. Blocked or overdue work is surfaced as a signal with a proposed way forward, and progress/decay/needs-you are shown as data signals.

## SDD
The console is an ABA-generated React + Vite + TypeScript + shadcn frontend reading through one swappable data-access module. Nitro is only the thin session/credential adapter. Octo remains canonical for entities, claims, evidence, files, RAG, and the FalkorDB graph; the workspace SQL surface holds operational records (agents, runs, approvals, projects, missions). Multi-tenancy is Organization → workspace → project, backed by Octo principals/memberships and the private/shared split. The intelligence layer is a real orchestrator over the model gateway plus Octo RAG/graph/MCP research, gated by the existing autonomy and approval model. Voice/phone reuses the Riley LiveKit agent. The trust layer (propose-don't-decide, deadline/iteration loop, signal layer) extends PROJECT.md rules without replacing them.

## Eval / Completion Oracle
Sign-in and guest login both work. The container switcher scopes work. The Project→Objective→Mission→Plan chain is visible and linked, and people are not duplicated into projects. The copilot routes a request to the right agent and can run a research/design pass that proposes a mission name, objective, and plan held for approval. A blocked/overdue mission produces a signal plus a proposed adjustment rather than stalling silently. Approvals gate every send/call/publish/commit. Real user-flow verification runs against a seeded workspace, then against Octo once wired; required gates pass on the exact candidate.
